The Pluggable CLP Connector for Presto Native: Specialized Storage for Semi-Structured Data

Variant is standardizing how semi-structured values move through the lakehouse. Presto gives storage systems a common SQL surface, but neither a common value type nor a table contract determines how nested paths and recurring text are physically organized, compressed, or searched.

That distinction matters when an analytical platform cannot control the applications producing logs, traces, audit records, or AI coding-agent sessions. Fields, nesting, types, and messages evolve independently. JSON preserves that long tail but gives up field-level columnar execution. A global schema requires coordination the platform rarely has.

The open-source CLP project from YScope addresses that physical problem with a native columnar format and search engine for semi-structured data. At Uber, currently onboarded ML/AI, streaming, and data-platform workloads produce about 25 PB of raw logs per month, making storage layout a material concern rather than an implementation detail. Core ideas behind CLP's storage model are described in the OSDI '24 paper “μSlope: High Compression and Fast Search on Semi-Structured Logs”.

YScope's August 2025 post, “Querying CLP-compressed logs with SQL via Presto”, explains the original storage model, SQL access, pushdown, and integration. That implementation ran CLP natively in the Velox workers of a Presto fork. Since then, Variant has become the lakehouse reference across SQL, table, and file layers, while CLP has become available through a pluggable Presto Native connector. This article asks where their physical work differs and then follows the connector from SQL to its coordinator–worker boundary.

Variant in the Lakehouse Landscape

Variant is a typed dynamic value rather than a fixed record schema or JSON text. Rows may have different nested shapes while preserving scalar types. It standardizes what supporting systems exchange, not how nested fields are laid out for scanning.

The lakehouse Variant stack assigns each layer a role. A query engine supplies the SQL type and operators. Trino provides them today and its Iceberg connector connects the stack, making it useful precedent in the Presto lineage. Iceberg v3 defines the table type. Parquet defines the metadata and value encoding and optional shredding. The Parquet project's overview and Databricks' introduction provide further background.

Unshredded Variant is a Parquet binary column of row-local dynamic values. It supports typed path navigation without parsing text, but inner fields lack independent Parquet encodings and statistics. Shredding promotes writer-selected paths such as request.id into typed columns for field-level compression, projection, statistics, and skipping. The value representation preserves everything else.

Selective shredding fits interoperable tables when writers know the hot paths before opening each file for writing. Changing that selection later requires rewriting the file. One typed_value column represents one declared type for a shredded field. Other types remain in value. Promoting every path and type would instead create a wide, sparse physical union with extra schema and metadata overhead.

CLP: Native Columnar Semi-Structured Storage

YScope's August 2025 post gives the full introduction to Encoded Record Tables (ERTs), Merged Schema Trees (MSTs), logtypes, and the original Presto integration. Only two physical ideas need repeating here: how CLP organizes document structure and how it decomposes recurring text.

At the document-structure level, Parquet Variant is value-first: one table per file with row-level Variant values and selected shredded columns. CLP is column-first. A useful mental model is one archive containing many shape-specific columnar subtables behind a single logical event stream. Each immutable CLP archive independently defines its own ERTs. They are internal storage structures, not SQL tables. Each ERT stores records sharing one combination of keys and value types in homogeneous columns. The archive-local MST merges those schemas into one inventory and maps each path and type to its physical columns. It is execution metadata local to the archive, not a global table schema.

Even comprehensively shredded Variant retains one file-wide schema, so a field absent from a row becomes a missing entry in an optional column. Parquet encodes that sparsity compactly through definition levels rather than literal null payloads. CLP instead represents structural absence by placing the record in an ERT without that field. Explicit source nulls remain preserved.

CLP's second level of structurization is inside string values. It infers logtypes, format-string-like templates that encode recurring static text once, and stores the extracted variable values in separate typed ERT columns. Shredding a Variant path as a string leaves its contents whole unless another index parses it. When structure, static text, and values recur, ERT and logtype locality improve compression. The same locality narrows structural and text searches to relevant encoded columns and streams without reconstructing every string.

These advantages remain workload-dependent. CLP fits when the platform cannot control upstream schemas or preselect useful paths and needs cross-field or free-text search with compact archives that reduce object-storage transfer and request costs. Variant with selective shredding fits interoperable lakehouse tables with predictable hot paths. With one stable schema, a typed Parquet layout or comprehensively shredded Variant columnizes the same fields as CLP. With nearly unique shapes, CLP's recurring-shape locality fades.

From Predicate to Physical Scan: Parquet Variant and CLP

The earlier YScope walkthrough traces typed accessors through rewriting, split discovery, pushdown, and native execution. Here, the comparison begins after pushdown: which physical data must the reader touch?

Predicate Parquet Variant CLP
Exact named path Use a shredded column if selected, or traverse value otherwise Resolve the path and type once per archive split, then scan matching ERT columns
Same path, multiple value types Use typed_value for its declared type. Other types remain in value Route each type to its own homogeneous ERT columns
Cross-field typed value search Inspect each row's relevant value structure unless another index covers the search Resolve candidate paths from the archive MST, then scan the corresponding encoded columns

Exact paths can be efficient in either layout when Variant has shredded them. Otherwise, Variant inspects relevant value pages and each selected row's binary structure, while CLP resolves compatible ERT columns once per archive split. Current CLP predicates can also search typed values over wildcard keys.

Those scans depend on two metadata layers: a metastore that plans across files and metadata inside each selected CLP archive.

Beyond File Pruning: Leveraging Metastore and CLP Metadata

Metastore planning is format-independent. Before creating splits, a provider can use time bounds, dimensions, and statistics to prune either form of CLP storage: compressed key-value intermediate representation (KV-IR) files that are appendable, streamable, and searchable, or compact immutable archives. Both forms are designed for streaming search. Most analytical metastores support this. Uber's internal metastore applies it across billions of files with a modest operational footprint.

Trustworthy per-file time bounds can also enable a specialized, proof-based form of Top-N file-enumeration early termination for eligible newest-first queries such as ORDER BY timestamp DESC LIMIT N. This is not ordinary LIMIT short-circuiting. Uber enumerates files by descending maximum timestamp and uses exact per-file matching counts for supported predicates. Once the count reaches N, the provider freezes the earliest timestamp covered, includes every file overlapping that watermark, and stops only when the next file is strictly older. Unsupported row-level predicates disable the guarantee. Time sorting and append-only publication help but are not required.

Once a file becomes a split, column statistics and indexes remain a conventional baseline. CLP additionally stores its archive-local MST and dictionaries for logtypes and values in the archive header. The MST provides the complete path/type-to-column map, while logtype metadata captures structure inside text values. A worker can initialize from that compact metadata, identify candidate columns, and stream without local staging. The metastore chooses the files; CLP metadata narrows the work inside each archive.

At Uber, the roughly 25 PB of raw logs produced each month compress to 750–850 TB, while five 48-core workers serve CLP data from object storage. The connector presents both metadata layers through an ordinary Presto catalog.

Deploying and Querying with the CLP Connector

From a Presto user's perspective, the result is ordinary SQL over storage-native scans. One query can combine exact typed paths, cross-field search, and complete-event reconstruction:

SHOW TABLES FROM clp.default;

SELECT
    CLP_GET_STRING('service.name') AS service,
    CLP_GET_BIGINT('response.status') AS status,
    CLP_GET_JSON_STRING() AS event
FROM clp.default.application_logs
WHERE CLP_GET_BIGINT('response.status') >= 500
  AND CLP_WILDCARD_STRING_COLUMN() LIKE 'timeout%'
LIMIT 100;

Replace application_logs and the paths with a deployed dataset. Typed accessors state the expected runtime type. The wildcard-key predicate searches string fields without naming an exact key. Full JSON is reconstructed only for projected matches. An optional Presto table schema, called a convenience schema, can expose frequently used CLP paths as ordinary typed columns. Only the SQL interface changes because the ERT columns already exist. YScope's August 2025 walkthrough covers rewriting and pushdown.

For an operator, the deployment path is short: ingest with CLP, install the matched Java coordinator plugin and native worker bundle, enable the worker loader, and create etc/catalog/clp.properties. The documented setup reads MySQL metadata populated by the YScope CLP OSS package. Custom providers can replace it. The connector is read-only and exposes discovered datasets in its default schema. Its packaging flow supports OS packages, tarballs, and an init-container image.

Two Compose examples make the deployment concrete. The connector's coordinator/native-worker stack installs matched artifacts through the shipped installer image. The CLP deployment stack places the coordinator and worker in a complete CLP environment.

Behind that short operator path is a two-part coordinator–worker contract.

Building Pluggable Presto Native Connectors: Lessons from CLP

An out-of-band connector for Presto Native, documented under Presto C++, must bridge two runtimes: the Java coordinator and Velox-based native workers. YScope engineers collaborated with the Presto community to build the CLP connector as one of the first end-to-end plugins across that boundary, making it a practical reference for this extension path. The earlier integration already ran CLP natively in workers, but integrated at the Velox execution-framework layer, with corresponding extensions in the forked Presto/Prestissimo codebase. It was an in-tree native integration, not an external plugin. The current connector instead integrates at the Presto Native worker-plugin boundary. It builds as a separate library against Presto and Velox headers, and each worker loads it out of band. Native execution moved out of the fork, not out of the worker.

Through Presto's data-source model, the Java plugin presents CLP as catalogs, tables, and splits, while the native library retains archive-specific execution. A query may span compressed KV-IR files and compact immutable archives without turning their local structure into a catalog-wide union:

Define the coordinator–worker contract. Start with tables, types, splits, pushdowns, residual behavior, and the handles that cross the boundary. The Java side publishes the connector factory, metadata, split manager, functions or optimizer, and handle codecs. CLP's ClpPlugin and ConnectorCodecProvider are concrete examples. The native bundle exports one registerExtensions entry point, registers the Velox connector factory and handle adapter, and returns columnar batches. plugin.dir locates the bundle. A linker version script exposes only the entry point.

Two Presto hooks complete that contract. PR #27653 added factory registration from dynamically loaded code. PR #27652 added connector-specific native deserialization. With use-connector-provided-serialization-codecs enabled, workers can discover the native factory and decode handles produced by Java. Execution stays in process, avoiding sidecar RPC and per-record language bridges.

Package one compatible unit. CLP builds on manylinux_2_28 for amd64 and arm64, stages the coordinator JAR separately from the worker .so, puts non-system dependencies under lib/, and sets RUNPATH to $ORIGIN/lib. The same payload feeds OS packages, tarballs, or an init-container image. Compatibility includes libc, Presto Native, Velox, and CPU flags. Folly's F14LinkCheck verifies its CPU-intrinsics mode across dlopen, so the CLP build reuses Velox's get_cxx_flags helper.

Test the deployed boundary. Query-runner tests cover catalog discovery, split planning, codecs, and handle serialization. Dependency-free native helpers remain independently testable. Registration, deserialization, data sources, and vectors need a real worker because their symbols resolve at runtime. CLP's cumulative integration-test stack makes task integration-tests:run build the installer and launch a Java coordinator and native worker over local and S3 archive fixtures.

For an external connector author, the reusable deliverable is the tested coordinator artifact, native bundle, and serialized protocol together.

Conclusion: Choosing Semi-Structured Storage for Presto

There is no universal storage model for semi-structured data. The lakehouse Variant stack fits when cross-engine portability matters and writers can identify paths for shredding before writing. CLP fits when the analytical platform cannot control upstream schemas or content, recurring structure and text can be exploited, and users need to search across fields they could not predict at ingestion. Stable schemas and nearly unique shapes reduce CLP's advantages.

The models are complementary rather than interchangeable. A future PrestoDB Variant type could give Parquet and CLP one SQL interface, but Parquet would still read value or shredded columns while CLP binds paths to ERT columns and encoded text streams. The open-source CLP connector demonstrates the larger Presto lesson: common SQL and planning can coexist with storage-specific native execution behind a pluggable connector boundary.
